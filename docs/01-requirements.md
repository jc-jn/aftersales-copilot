# 01. 需求规格

## 1. 功能范围

### 1.1 认证与账号

- 邮箱或用户名 + 密码登录；演示环境提供固定测试账号。
- JWT Access Token + Refresh Token；密码使用 BCrypt。
- 管理员可启停客服账号，不能查看用户密码或模型密钥明文。
- 第一版不实现注册验证码和第三方登录，可由管理员创建账号或开放简单注册。

### 1.2 模拟电商数据

- 商品、SKU、品牌、类目、价格、序列号要求、质保月数。
- 订单和订单项，状态至少包含 `PAID`、`SHIPPED`、`DELIVERED`、`CANCELLED`。
- 支付记录只表达支付事实，不接支付网关。
- 物流记录包含运单号、承运商、节点和签收时间。
- 一个工单只绑定一个订单项；一个订单项可以存在多个历史工单，但同一时刻最多一个未终结工单。

### 1.3 工单

- 创建时选择订单项、期望售后类型、问题描述，可上传最多 5 个附件。
- 创建前校验订单归属、订单状态、重复活跃工单和基础售后时间窗口。
- 支持用户补充信息、取消未执行工单、查看时间线。
- 支持客服领取、自动分配、手动转派、追加内部备注和回复。
- 内部备注对消费者不可见；公开消息双方可见。
- 工单关闭后不再允许业务操作，只允许查看和评价。

### 1.4 AI 能力

- 意图分类：四类售后或 `OTHER`。
- 紧急度：`LOW`、`MEDIUM`、`HIGH`、`URGENT`，但最终 SLA 由 Java 规则决定。
- 信息抽取：商品、故障、发生时间、是否签收、是否拆封、序列号、用户诉求等。
- 缺失信息识别：生成需要用户补充的问题。
- RAG：根据商品、类型和问题检索售后政策、FAQ、说明书。
- 回复建议：仅供客服编辑；包含依据和不确定性提示。
- Tool Calling：查询订单、物流、质保、工单历史。
- 处理提案：输出结构化建议，不直接执行。
- 结案摘要：总结问题、证据、处理动作和最终结果。
- 失败转人工：超时、无证据、模型错误、提示注入或结构化输出校验失败时降级。

### 1.5 知识库

- 管理员创建知识库并上传 PDF、DOCX、Markdown、TXT；MVP 演示资料优先用 Markdown/PDF。
- 文档状态：`UPLOADED`、`PARSING`、`INDEXED`、`FAILED`、`ARCHIVED`。
- 支持版本号、适用商品/类目、有效期、启停和重新索引。
- 删除业务文档时先标记归档，再异步删除 Qdrant 向量，避免直接物理删除造成审计缺失。
- 回答必须过滤无权限、已归档、未生效或已过期文档。

### 1.6 统计

- 工单数量、类型分布、平均首次响应时间、平均解决时间。
- AI 分析成功率、转人工率、AI 建议采纳率。
- 按客服统计待处理数和解决数，不做绩效排名。
- 模型调用次数、Token、估算成本和异常次数。

## 2. 业务规则

### 2.1 售后类型

| 类型 | 枚举 | MVP 规则 |
|---|---|---|
| 仅退款 | `REFUND_ONLY` | 无需寄回商品；Java 校验订单项、已退金额和政策窗口后执行模拟退款 |
| 退货退款 | `RETURN_REFUND` | 用户确认方案后生成模拟退货单；收货检查通过后执行模拟退款 |
| 换货 | `EXCHANGE` | 用户寄回，检查通过后生成模拟补发单；不进行真实库存扣减，可记录模拟库存动作 |
| 维修 | `REPAIR` | 生成维修单，记录收件、检测、维修、寄回节点 |

AI 可建议类型，但用户提交的期望类型不会被 AI 静默修改。客服变更类型时必须记录原因。

### 2.2 工单状态

权威状态由 Java 管理。AI 状态、文档状态和提案状态单独保存，不能混入工单状态。

| 状态 | 含义 |
|---|---|
| `SUBMITTED` | 已提交，尚未进入客服队列 |
| `PENDING_ASSIGNMENT` | 等待分配客服 |
| `PENDING_AGENT` | 等待客服处理 |
| `PENDING_CUSTOMER` | 等待用户补充信息或确认方案 |
| `WAITING_RETURN` | 等待用户寄回商品 |
| `RETURN_IN_TRANSIT` | 用户已填写退货物流 |
| `RETURN_RECEIVED` | 商家模拟收货，等待检查/后续处理 |
| `PROCESSING` | 正在模拟退款、换货或维修处理 |
| `RESOLVED` | 业务处理已完成，等待关闭/评价 |
| `REJECTED` | 售后申请被拒绝，已记录理由 |
| `CANCELLED` | 用户或管理员在允许阶段取消 |
| `CLOSED` | 最终关闭，不允许再推进业务状态 |

创建后立即写入 `SUBMITTED`。无论 AI 是否成功，Java 都应在任务投递后将其推进到 `PENDING_ASSIGNMENT`。自动分配成功后进入 `PENDING_AGENT`。

### 2.3 状态转换

| 当前状态 | 动作 | 目标状态 | 操作者 |
|---|---|---|---|
| `SUBMITTED` | 入队完成 | `PENDING_ASSIGNMENT` | 系统 |
| `PENDING_ASSIGNMENT` | 分配/领取 | `PENDING_AGENT` | 系统/客服/管理员 |
| `PENDING_AGENT` | 请求补充信息 | `PENDING_CUSTOMER` | 客服 |
| `PENDING_CUSTOMER` | 用户补充 | `PENDING_AGENT` | 用户 |
| `PENDING_AGENT` | 用户确认需寄回的提案 | `WAITING_RETURN` | 用户触发、系统执行 |
| `WAITING_RETURN` | 填写退货物流 | `RETURN_IN_TRANSIT` | 用户 |
| `RETURN_IN_TRANSIT` | 确认收货 | `RETURN_RECEIVED` | 客服/管理员 |
| `RETURN_RECEIVED` | 检查通过并执行 | `PROCESSING` | 客服 |
| `PENDING_AGENT` | 确认仅退款提案并执行 | `PROCESSING` | 客服/用户确认后系统 |
| `PROCESSING` | 执行成功 | `RESOLVED` | 系统 |
| 可拒绝状态 | 拒绝 | `REJECTED` | 客服/管理员 |
| 未进入 `PROCESSING` 的活动状态 | 取消 | `CANCELLED` | 用户/管理员 |
| `RESOLVED`/`REJECTED`/`CANCELLED` | 关闭 | `CLOSED` | 用户/系统/管理员 |

`RETURN_REFUND`、`EXCHANGE`、`REPAIR` 必须经过寄回链路；`REFUND_ONLY` 不进入寄回状态。状态机必须拒绝非法跳转并返回当前版本。

### 2.4 提案规则

- 提案状态：`DRAFT`、`PENDING_CONFIRMATION`、`CONFIRMED`、`REJECTED`、`EXPIRED`、`EXECUTED`、`FAILED`。
- AI 创建的提案必须由客服审核后才能发送给用户；客服创建的提案可直接发送。
- 每张工单同一时刻最多一个 `PENDING_CONFIRMATION` 提案。
- 提案包含有效期，默认 24 小时；过期后需重新创建。
- 确认接口必须携带 `Idempotency-Key` 和工单 `version`。
- 提案金额不能超过订单项可退金额；AI 输出金额不可信，Java 必须重新计算。
- 提案被执行后不可修改；失败可以在排除原因后以新幂等键重试同一提案。

### 2.5 分配规则

1. 工单进入 `PENDING_ASSIGNMENT`。
2. 从启用且在线/可接单客服中，选择活动工单数最少者。
3. 并列时选择最久未分配者。
4. 使用数据库条件更新或分布式锁避免并发重复分配。
5. 没有可用客服时保持待分配，由管理员手动分配。

## 3. 用户故事与验收标准

### US-01 创建工单

作为消费者，我可以从自己的已签收订单项创建售后工单。

- 不能为他人订单创建工单。
- 同一订单项存在活动工单时返回明确冲突错误。
- 创建成功后返回工单号和状态，并能在时间线看到提交事件。

### US-02 AI 辅助客服

作为客服，我可以看到 AI 分类、缺失信息、回复建议和引用。

- AI 结果标注模型、版本和生成时间。
- 引用可以定位到知识文档章节。
- 客服可以编辑回复；系统保存 AI 原文、最终发送内容和采纳关系。

### US-03 安全执行提案

作为用户，我确认客服发送的仅退款方案后，系统执行模拟退款。

- 重复点击只能产生一次退款记录。
- 金额由 Java 根据订单与规则计算。
- 非本人、过期提案、错误工单版本均被拒绝。
- 执行过程和结果进入审计日志与工单时间线。

### US-04 AI 降级

作为客服，当模型不可用时仍可以正常处理工单。

- AI 超时不会导致创建工单失败。
- 页面显示“AI 暂不可用”，允许人工分类、回复和创建提案。
- 管理员可以对失败任务重试，但不会重复写入业务动作。

## 4. 非功能需求

- API 响应采用统一错误码和 `traceId`。
- 所有列表分页；默认 20，最大 100。
- 使用乐观锁避免客服和用户并发覆盖状态。
- 附件必须限制格式、大小和访问权限；下载使用短期签名 URL。
- 敏感配置只通过环境变量或密钥文件注入。
- 核心业务操作写审计日志，审计日志不可由普通用户修改。
- AI 输出必须经过 JSON Schema/Pydantic 校验；不得直接拼接 SQL 或内部 URL。
